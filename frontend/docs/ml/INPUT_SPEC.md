# 수어 단어 분류 엔드포인트 입력 규격

이 문서는 SageMaker 엔드포인트에 보내는 요청과 응답, 그리고 서버가 하는 전처리를 정의한다. 학습 데이터를 만든 계산(`detector/holistic.py` → `build_final.py --mode ar` → `train_svm.build_features`)과 같은 계산을 `code/sign_features.py` 한 곳에 옮겨 두었고, 1~7항의 원시 프레임 요청에서는 클라이언트가 MediaPipe가 돌려준 원시 좌표만 보내고, 정규화·각도 계산·30프레임 맞춤을 클라이언트에서 따로 구현하지 않는다. 명세서 형식인 0항의 (30, 49, 2) 요청은 이와 달리 브라우저가 정규화와 30프레임 맞춤을 해서 보낸다.

## 0. 현재 형식: 명세서 입력 (30, 49, 2)

`train_final_2d.py`로 학습한 모델(`meta.json`의 `"input": "spec2d"`, 178개 클래스)은 브라우저가 정규화해서 보낸 좌표를 그대로 받는다. 아래 1~7항의 원시 프레임 요청(`frames`)은 `webcam_test.py`와 이전 모델용이며, 이 모델도 받아서 같은 형식으로 바꿔 준다(`code/spec2d.py`).

```json
{"top_k": 5, "keypoints": [ [ [x, y], ... 49개 ], ... 30프레임 ]}
```

**좌표 형식** (기준 구현: `code/spec2d.py`의 `frame_points`, `resample_points`)

| 항목 | 내용 |
|---|---|
| 모양 | 프레임 30 x 지점 49 x 축 2 (x, y). 다른 모양은 서버가 오류를 낸다 |
| 지점 0~6 | 코, 왼어깨, 오른어깨, 왼팔꿈치, 오른팔꿈치, 왼손목, 오른손목 (MediaPipe 포즈 0, 11, 12, 13, 14, 15, 16) |
| 지점 7~27 / 28~48 | 왼손 21점 / 오른손 21점 (MediaPipe 손 순서). 왼손은 포즈의 왼손목에 붙은 손(수어자 본인 기준) |
| 원점, 척도 | 원점 = 두 어깨(포즈 11, 12)의 중점, 척도 = 두 어깨 사이의 거리. **둘 다 픽셀 단위**로 잰다. 즉 x에 영상 너비, y에 영상 높이를 곱한 좌표로 계산한다 |
| 값 | `(점 − 원점) / 척도`. 검출 안 된 손은 21점 모두 0 |
| 프레임 선택 | 포즈가 없거나 두 손이 모두 없거나 어깨 너비가 영상 너비의 0.1% 미만인 프레임은 버린다 |
| 30프레임 맞추기 | 남은 프레임을 시각 기준 균등한 30개 시점으로 맞춘다. 앞뒤 프레임을 선형 보간하되, 어느 한쪽에서 그 손이 검출되지 않았으면 보간하지 않고 가까운 쪽 값을 쓴다 |
| 전송 크기 | 좌표를 소수 4자리로 반올림해 보내면 요청이 약 24KB(최대 24.4KB, 공백 없는 JSON)다. API Gateway WebSocket의 프레임 한도 32KB 안에 들어간다. 팀 val 198클립에서 1위는 전체 자릿수 때와 모두 같았고 1위 확률은 최대 0.0001 달랐다. 소수 6자리는 약 30KB, 전체 자릿수는 약 64KB다 |

- 종횡비: 픽셀 단위로 재므로 영상 크기가 달라도 같은 값이 나온다. 0~1 정규화 좌표를 그대로 쓰면 y가 학습 데이터보다 늘어나 정확도가 떨어진다.
- 좌우 반전하지 않은 프레임으로 MediaPipe를 돌린다. 화면 표시용으로만 반전한다.
- 모델은 코와 어깨(지점 0~2)를 쓰지 않는다(카메라 높이 차이에 약해서 뺐다). 형식상 49점을 모두 보낸다.
- 단어 구간 자르기(손을 내린 앞뒤)는 프런트가 한다. 모델에는 한 단어 구간의 프레임만 들어가야 한다. 구간 경계가 어긋났을 때의 영향과 프런트 권장 사항은 아래 "구간 경계 오차"에 정리했다.
- 학습 데이터는 AI Hub 86개 클래스(우리가 MediaPipe로 추출한 16명)와 수어사전 92개 클래스(팀 데이터셋, 수어자 1명)다. 수어사전 클래스는 수어자가 1명이라 정확도를 평가하지 못했다. 웹캠으로 한 확인은 아래 "수어사전 전용 클래스 확인"에 있다.

**응답**

```json
{"ok": true, "frames_in": 30, "frames_used": 30,
 "top_k": [{"label": "화상", "name": "화상", "label_id": 53, "word_id": 71, "prob": 0.62}, ...]}
```

`label`과 `label_id`가 결과를 식별하는 기준이다. `label_id`는 팀 데이터셋의 `index.csv`에 있는 `label_id`(0~177)와 같다. `word_id`는 참고용 AI Hub 단어 id이고, 수어사전 전용 클래스에는 없으며, 여러 AI Hub 단어 id를 한 클래스로 합친 경우(예: 없다)에는 대표 id 하나만 나간다. 결과 처리에 `word_id`를 쓰지 않는다. `keypoints` 대신 `frames`를 보내면 위 규칙으로 서버가 바꾼다(프레임 부족이면 `{"ok": false, "reason": ...}`).

**최종 모델 (`final_model_cnn_spec2d_c`)**

- 구조와 설정은 CNN(hidden 512, dropout 0.4, lr 0.01, wd 0.1, 300 epoch, label smoothing 0.4)이고 피처는 `spec2d_noface` 92열이다. 입력은 이 항의 (30, 49, 2)다.
- 학습 데이터는 우리가 MediaPipe로 추출한 AI Hub 86개 클래스(수어자 16명 전체와, 품질을 낮춘 변형 데이터 5종 `gesture_dataset_final_ar_mild`, `_medium`, `_sa1`, `_sa2`, `_severe`)와 수어사전 전용 92개 클래스(수어사전 원본 93개와 팀 데이터셋의 증강 829개를 합친 922개)다. 수어사전은 이 밖에 AI Hub 클래스인 "상처/다치다" 클립 1개도 가지고 있다.
- AI Hub 샘플마다 구간 경계 오차를 준 복사본 1벌을 더했다(`--perturb_train 1`). 각 복사본은 앞뒤 끝마다 50% 확률로 0~30%를 잘라내거나, 아니면 0~50%만큼 첫·끝 프레임을 붙잡아 늘린다.
- 수어사전 922개는 수어자가 1명뿐이라, 같은 클립을 8번 되풀이하는 대신 2번 되풀이하고 클립마다 수어자 차이를 흉내 낸 복사본 6벌을 더했다(`--sldict_repeat 2 --sldict_aug 6`, 전체 샘플 수는 8번 되풀이할 때와 같다). 복사본에는 경계 오차도 같이 준다. 수어자 차이 증강(`spec2d.augment_signer`)은 전체 크기 0.85~1.15배와 x, y 따로 ±8%, 회전(표준편차 6도), 팔꿈치·손목·손의 위치 이동(표준편차가 어깨 너비의 0.12), 손 좌표 잡음(표준편차 0.01), 동작 속도(시간축을 0.8~1.25 범위의 지수로 왜곡)이다. 이 크기들은 임의로 정한 값이다.
- 이 모델은 전체 수어자로 학습해서 따로 평가한 수치가 없다. 아래의 경계 오차 수치는 같은 설정에서 수어자 REAL02, REAL06을 빼고 학습한 모델로 잰 값이다. 그 평가에서 깨끗한 영상 197개의 1위 정확도는 100%였다(경계 오차 증강을 넣은 모델과 넣지 않은 모델, 수어사전 증강까지 넣은 모델이 모두 같았다).
- 재현 명령(프로젝트 루트에서): 평가는 `python deploy\train_final_2d.py --holdout REAL02,REAL06 --boundary_eval --perturb_train 1 --sldict_repeat 2 --sldict_aug 6`이다. 증강 없는 모델은 증강 옵션을 모두 빼고, 경계 오차 증강만 넣은 모델은 `--perturb_train 1`만 붙여 같은 평가를 돌렸다. 평가 명령은 모델을 저장하지 않는다. 최종 모델은 `python deploy\train_final_2d.py --perturb_train 1 --sldict_repeat 2 --sldict_aug 6 --out_dir ..\final_model_cnn_spec2d_c`로 만들었다.

**수어사전 전용 클래스 확인**

수어사전 전용 92개 클래스는 수어자가 1명이라 정확도를 평가하지 못했다. 대신 웹캠 테스트 페이지(`webcam_test.py`)로 저장한 녹화 13개(화상 3, 체온 3, 검사 7)를 `deploy\eval_recordings.py`로 채점했다. 녹화에 적힌 단어 이름을 정답으로 보고, 후보 178개 중 정답의 순위를 센다. 화상과 체온은 AI Hub로 학습한 클래스이고, 검사(`label_id` 12)는 수어사전 전용 클래스다. 이 녹화들은 학습에 쓰지 않았다.

| | 수어사전 증강 없음 (`_b`) | 수어사전 증강 (`_c`) |
|---|---|---|
| 화상·체온 1위 정답 | 6/6 (확률 0.51~0.65) | 6/6 (확률 0.46~0.63) |
| 검사 1위 정답 | 0/7 | 0/7 |
| 검사 정답 순위 | 6, 7, 21, 2, 11, 4, 6 | 3, 3, 9, 27, 5, 3, 2 |
| 검사 정답 순위 중앙값 | 6위 | 3위 |
| 전체 13개 중 정답이 상위 5개 안 | 8개 | 11개 |

- 수어사전 증강으로 검사의 정답 순위는 올랐지만 1위로 맞힌 것은 없었고, 정답 확률도 0.01~0.04에 그쳤다. 영상 7개, 클래스 1개, 수어자 1명의 결과라서 개선이 우연일 가능성도 있다.
- 1위가 틀린 영상 7개는 모두 수어사전 전용 단어(검사)였고 1위 확률이 0.14 이하였다. 맞은 영상 6개는 0.46 이상이었다. 이 간격은 오답이어서가 아니라 수어자 1명으로만 학습한 단어여서 생겼을 가능성이 있고, 표본도 작아 임계값의 근거로 쓸 수 없다.
- 수어사전 전용 클래스를 실제로 맞히려면 다른 수어자의 영상이 필요하다고 본다. 증강만으로는 1위 정확도가 올랐다는 증거를 얻지 못했다.
- 검사의 녹화는 AI Hub 단어 29와 1129로 적혀 있지만, 두 단어는 우리 AI Hub 학습 단어 99개에 없다. 모델은 수어사전의 검사 클래스로 판정한다.

**팀 데이터셋 val 평가**

팀 데이터셋(`최종`)의 val(aihub02, aihub06, AI Hub 86개 클래스, 198클립)은 OpenPose 키포인트를 (30, 49, 2)로 변환한 것이다. 이 두 수어자는 우리 데이터의 REAL02, REAL06과 같은 영상이다. 이 둘을 빼고 학습한 모델(`--holdout REAL02,REAL06 --save`, 최종 모델과 같은 설정)로 후보 178개 전체에서 `deploy\eval_team.py --model_dir <모델>`로 채점했다.

| | 클립 | 1위 정확도 | 상위 5 | 팀 기준 모델(1-NN) |
|---|---|---|---|---|
| 전체 | 198 | 97.98% | 98.48% | 78.8% |
| 진료 76개 단어 | 176 | 98.86% | 98.86% | 85.2% |
| 숫자 1~10 | 22 | 90.91% | 95.45% | 27.3% |
| aihub02 | 99 | 95.96% | 96.97% | 84.8% |
| aihub06 | 99 | 100.00% | 100.00% | 72.7% |

- 팀 기준 모델의 값은 팀 데이터셋 README에 적힌 수치다. 기준 모델의 후보 구성은 README에 없다. 후보를 AI Hub 86개로 좁혀도 우리 모델의 1위 정확도는 같았다.
- 틀린 4개는 모두 aihub02의 매일(`WORD0932`), 엄마(`WORD1528`), 2(`WORD2633`), 10(`WORD2641`)이고 전부 "춥다"(확률 0.24~0.40)로 나왔다. 이 클립들은 프레임 간 움직임이 0.002 안팎으로 val 중앙값(0.063)보다 훨씬 작고(val 하위 2% 이내), 손목이 어깨 너비의 약 1.5배 아래에 있어 손을 내린 채 가만히 있는 자세다. 엄마 클립은 원본 31프레임 중 쓸 수 있는 프레임이 2개다. 수어 동작이 담기지 않은 키포인트로 보이며, 원본 영상은 확인하지 못했다. 우리 MediaPipe 버전의 같은 수어자 영상은 197개가 모두 맞았다.
- 한계: val이 198클립이라 한 개가 0.5%p, 숫자는 22클립이라 한 개가 4.5%p다. 입력이 OpenPose 변환이라 실제 서비스 입력인 브라우저 MediaPipe와의 차이는 이 평가에 들어 있지 않다.
- 전체 수어자로 학습한 최종 모델로 val을 채점하면 같은 97.98%가 나오지만, val 수어자가 학습에 들어 있으므로 새 수어자 정확도가 아니다. 같은 모델로 팀 데이터 전체를 채점하면(`--all`) AI Hub 원본은 train 수어자 99.75%, val 수어자 97.98%다. 팀의 AI Hub 증강 클립은 77.10%인데, 팀 README에 따르면 이 증강에는 좌우 반전(30%)이 들어 있고 우리 모델은 증강 클립으로 학습하지 않았으므로 실제 입력의 성능으로 보지 않는다.

**구간 경계 오차**

빼 둔 수어자 REAL02, REAL06의 깨끗한 영상 197개에서, 30프레임으로 만든 샘플의 앞뒤를 잘라내거나(crop) 첫·끝 프레임을 붙잡아 늘린(pad) 뒤 다시 30프레임으로 맞춰 1위 정확도를 쟀다. 비율은 구간 길이에 대한 값이다. 열은 학습에 넣은 증강의 종류다.

| 조건 | 증강 없음 | 경계 오차 증강 | 경계 오차 + 수어사전 증강 (최종) |
|---|---|---|---|
| 원본 | 100.00% | 100.00% | 100.00% |
| crop 앞뒤 0.2 | 98.98% | 99.49% | 100.00% |
| crop 앞뒤 0.3 | 93.40% | 98.48% | 98.48% |
| crop 앞뒤 0.4 | 78.17% | 89.85% | 89.85% |
| crop 앞만 0.3 (동작이 늦게 시작) | 94.42% | 99.49% | 98.98% |
| crop 뒤만 0.3 (동작이 일찍 끝) | 98.98% | 99.49% | 100.00% |
| pad 앞뒤 0.6 | 96.95% | 100.00% | 100.00% |
| pad 앞뒤 1.0 | 89.34% | 95.43% | 94.92% |

- 경계 오차 증강으로 학습하면 구간을 잘라 낸 경우와 늘려 잡은 경우 모두 정확도가 올랐고, 깨끗한 영상의 정확도는 그대로였다. 수어사전 증강을 더해도 이 결과는 클립 1개 이내로 같았다. 상위 5개 안에 정답이 들어가는 비율은 증강 없는 모델의 crop 0.4(96.45%) 외에는 모든 조건에서 99% 이상이었다.
- 프런트 권장: 단어 구간의 시작이 동작보다 늦어 앞부분이 잘리면, 끝이 일찍 끊길 때보다 더 떨어진다. 구간을 정할 때 손을 든 시점보다 앞에 여유를 두고 시작하는 쪽이 안전하고, 끝은 약간 일찍 끊어도 영향이 작다. 앞뒤를 각각 구간의 30%까지 잘라내도 학습에 넣은 범위라 98% 안팎을 유지하고, 각각 40%를 잘라내면 90% 안팎으로 떨어진다. 두 손이 모두 검출되지 않은 프레임은 모델에 넣기 전에 버려진다. 다만 손을 내린 대기 시간에 손이 검출되는지는 재지 않았고, 검출되면 그 프레임은 구간에 남는다. 버튼을 누른 뒤 유효 프레임 30개만 넣는 현재 방식을 모사하면 어휘 안 12개 중 9개만 맞았다(7.8).
- 한계: 수어자 2명, 197개 클립이라 클립 하나가 0.5%p이므로 100%에 가까운 값 사이의 작은 차이는 의미를 두지 않는다. pad는 마지막 프레임을 붙잡아 둔 모사라서 실제로 손을 올리고 내리는 동작과 다르다. 실제 구간 분리기를 붙인 뒤 다시 재야 한다.

**확률 임계값 실험**

응답의 1위 `prob`를 임계값으로 잘랐을 때 버려지는 맞은 답과 걸러지는 틀린 답의 수를 쟀다. `deploy\eval_threshold.py`가 같은 표를 다시 만든다. 라벨이 비어 있는 녹화(수어를 하지 않은 입력)는 정답이 없으므로 웹캠 집계에서 뺀다. 임계값을 정하는 것은 이 실험의 범위가 아니며, 아래 표는 선택에 쓸 수치다.

```

```

`holdout_cnn`은 REAL02, REAL06을 빼고 학습한 평가용 모델 폴더이고, 배포 대상이 아니다. 팀 val 198클립(새 수어자)을 이 모델로 채점한 결과는 다음과 같다. 1위가 맞은 것은 194개이고, 맞은 답의 1위 확률은 0.04~0.73(중앙값 0.45), 틀린 4개는 0.24~0.40이다.

|---|---|---|---|
| 0.10 | 197 | 1 | 4 |
| 0.15 | 192 | 6 | 4 |
| 0.20 | 188 | 10 | 4 |
| 0.25 | 181 | 16 | 3 |
| 0.35 | 150 | 46 | 2 |

- 틀린 답을 모두 걸러 내는 가장 낮은 임계값은 0.45이고, 이때 맞은 답의 절반가량(95개)이 함께 버려진다. 0.25에서는 맞은 답 16개를 버리고 틀린 답 1개를 거른다. 확률이 label smoothing(0.4)으로 눌려 있어서 맞은 답도 낮게 나온다.
- 틀린 답은 4개뿐이라 이 표로 임계값의 효과를 정밀하게 말할 수 없다. 구간 경계 오차를 준 입력(틀린 답 6개)도 같은 경향이었다(0.45에서 맞은 답 84개를 버리고 틀린 답 0개).
- 마진(1위와 2위의 차이)으로 거른 결과는 확률로 거른 결과보다 낫지 않았다.
- 웹캠 녹화 13개(최종 모델)에서 맞은 6개는 0.46~0.63, 틀린 7개는 0.02~0.14였다. 틀린 7개가 모두 수어사전 전용 단어(검사)여서 임계값의 근거로 쓸 수 없다. 0.15 이상이면 이 녹화 7개는 전부 걸러진다.
- 수어 동작이 아닌 입력은 웹캠 녹화 12개(왼손 또는 오른손 하나만 든 동작, 1명, 구간을 자르지 않은 전체 녹화)로만 확인했다. 1위 확률은 0.020~0.107이었다(7.6, 7.7). 임계값 0.10에서는 1개(0.107)가 통과하고, 0.15 이상에서는 12개가 모두 거절된다. 0.15에서는 팀 val의 맞은 답 194개 중 6개(3.1%)가 함께 버려진다. 표본이 작아서 임계값을 정하려면 비수어 녹화가 더 필요하다.
- 수어를 한 입력이라도 모델 어휘에 없는 단어는 임계값으로 걸러지지 않았다. 학습 색인(`index.csv`)에 단어 번호가 없는 AI Hub 클립 11개 중 4개가 1위 확률 0.46~0.58로 틀린 단어를 냈고, 이 4개는 0.15, 0.25, 0.45에서 모두 통과한다. 0.60에서는 4개가 거절되지만 팀 val의 맞은 답 194개 중 172개가 함께 버려진다(7.9).

## 1. 흐름

웹캠 프레임 → MediaPipe Holistic (포즈, 왼손, 오른손) → 단어 하나에 해당하는 구간의 프레임 목록 → 엔드포인트(JSON) → 전처리 → 모델 → 상위 k개 단어와 확률

## 2. 요청 (`Content-Type: application/json`)

```json
{
  "width": 1280,
  "height": 720,
  "top_k": 5,
  "frames": [
    {
      "t": 0.000,
      "pose": [[x, y, z], ... 33개],
      "left_hand": [[x, y, z], ... 21개],
      "right_hand": null
    }
  ]
}
```

| 키 | 내용 |
|---|---|
| `width`, `height` | 좌표를 만든 영상 프레임의 픽셀 크기. 종횡비 보정에 쓴다. 필수 |
| `top_k` | 돌려줄 후보 수. 기본 5 |
| `frames[].t` | 프레임 시각(초). 그 프레임을 MediaPipe에 넣기 직전에 잰 촬영 시각을 쓴다(결과가 나온 시각이 아님). 시작 시각은 상관없고, 간격이 일정하지 않아도 된다. NaN이 없고 앞 프레임보다 작아지지 않아야 하며, 어기면 서버가 오류를 낸다(순번 간격으로 조용히 바꾸지 않는다). 한 프레임이라도 `t`가 없으면 최상위 `fps`로 순번/fps를 시간으로 쓴다 |
| `frames[].pose` | MediaPipe Holistic 포즈 33점. 각 점은 `[x, y, z]`이며 x, y는 0~1로 정규화된 이미지 좌표, z는 MediaPipe가 주는 상대 깊이 값 그대로. 검출 실패면 `null` |
| `frames[].left_hand`, `right_hand` | 손 21점. 검출 안 된 손은 `null` |

- 좌표는 가공하지 않고 MediaPipe 출력을 그대로 넣는다. 영상을 좌우반전해서 화면에 보여 주더라도 MediaPipe에 넣은 프레임과 같은 방향의 좌표를 보낸다(아래 6항).
- 포즈는 33점 전체를 보낸다. 서버는 그중 0, 9~16번만 쓴다.
- 프레임 속도는 10 fps 이상을 권장한다(7.2). 검출에 실패한 프레임은 건너뛰어도 되고 `null`로 보내도 된다.
- 요청 하나의 프레임 수는 최대 900개다. 프레임당 JSON 크기는 좌표를 전체 자릿수로 보내면 약 3.7 KB(49프레임에 180 KB)였다. 좌표를 소수 5자리로 줄여 보내면 더 작아진다.
- 오프라인 검증용으로 학습 CSV와 같은 형식의 `{"rows": [[255개 피처] ...], "times": [...]}`도 받는다.

## 3. 응답

```json
{
  "ok": true,
  "frames_in": 49,
  "frames_used": 49,
  "top_k": [
    {"label": "눈-1372", "name": "눈", "word_id": 1372, "prob": 0.91},
    {"label": "가렵다", "name": "가렵다", "word_id": 1101, "prob": 0.03}
  ]
}
```

- `label`은 학습 클래스 이름이다. 같은 이름의 다른 단어가 있을 때만 `이름-단어id` 형식이다. `name`은 id를 뗀 이름, `word_id`는 AI Hub 단어 id다.
- 사용할 수 있는 프레임이 5개 미만이면 오류가 아니라 `{"ok": false, "reason": "...", "frames_in": N, "frames_used": M}`을 돌려준다.
- 형식이 잘못된 요청(키 누락, 좌표 개수 불일치, NaN, 프레임 900개 초과, `t`와 `fps` 모두 없음, `t`가 NaN이거나 뒤로 가는 경우)은 서버가 오류를 낸다.
- `prob`은 softmax 확률이고, 학습 때 label smoothing을 썼기 때문에 확신도로 그대로 해석하기보다 후보 순위로 쓰는 편이 안전하다. 임계값은 실제 데이터로 정해야 한다.

## 4. 서버 전처리 (학습과 같은 정의)

1. 프레임마다 포즈가 없거나 두 손이 모두 없으면 그 프레임을 버린다.
2. 원점 = 두 어깨(포즈 11, 12)의 중점, 척도 = 두 어깨 사이의 거리(x, y 정규화 좌표에서의 유클리드 거리). 척도가 0.001 미만이면 그 프레임을 버린다.
3. 포즈와 손의 x, y는 `(값 − 원점) / 척도`, 포즈의 z는 `(z − 원점 z) / 척도`, 손의 z는 `z / 척도`.
4. 종횡비 보정: 3의 결과의 y에 `height / width`를 곱한다. 학습 영상(1920×1080)은 0.5625였고, 보정 전 학습 특징은 y가 약 1.78배 늘어나 있었다.
5. 손가락 관절각 30개(왼손 15 + 오른손 15)를 보정된 손 좌표 (x, y, z)로 계산한다. 검출 안 된 손은 좌표와 각도 모두 0.
6. 좌표는 소수 5자리, 각도는 소수 2자리로 반올림한다(학습 CSV와 동일).
7. 전처리는 프레임마다 피처 183개(포즈 상체 9점(0, 9~16) × xyz = 27, 양손 126, 각도 30)를 만들고, 모델의 `meta.json`에 적힌 `columns` 순서대로 그중 일부를 고른다. 피처 집합이 `all`이면 183개 전부, `noshoulder`이면 어깨(포즈 11, 12) 6개와 항상 0인 손목 z 2개를 뺀 175개, `noface`이면 `noshoulder`에서 코·입(포즈 0, 9, 10)의 x, y, z 9개를 더 뺀 166개다. 이전 최종 모델은 `noface`다(7.4). 열 이름이 `sign_features.model_columns()`에 없으면 모델을 불러올 때 오류를 낸다.
8. 남은 프레임을 시각 기준으로 균등 분할해 선형 보간하여 30프레임로 맞춘다.
9. 학습 데이터의 피처별 평균과 표준편차로 표준화한 뒤 모델에 넣는다. 표준편차가 1e-4 미만인 상수 피처는 0으로 둔다.

## 6. 아직 확인하지 못한 것

- **좌우 방향.** 학습 영상은 좌우반전 없이 MediaPipe에 넣어 추출했다(추출 코드에 반전 없음). 웹캠 화면을 거울처럼 뒤집어 보여 주는 경우에도 MediaPipe에 넣는 프레임은 반전하지 않은 원본이어야 학습과 같은 좌우가 된다. 반전된 프레임을 넣으면 왼손과 오른손, x 방향이 학습과 반대가 된다. 레거시 Holistic으로 사람이 왼손 하나를 든 웹캠 녹화에서 확인했다(7.6). 프론트와 같은 Tasks Vision의 Pose·Hand Landmarker는 AI Hub 수어 클립을 프레임으로 넣어 확인했고(7.5), 웹캠 앞에서 왼손 또는 오른손 하나를 든 녹화로도 확인했다(7.7). 반전하지 않은 입력에서는 손 라벨을 그대로 `left`, `right` 칸에 넣었을 때 든 손의 칸이 채워졌고(7.7에서 99.4%), 반전한 입력에서는 반대 칸이 채워졌다. 웹캠 녹화는 모두 수어가 아닌 동작이고, 웹캠 앞의 사람이 한 수어로는 재지 않았다.
- **MediaPipe 버전과 설정.** 학습 추출은 파이썬 `mediapipe==0.10.21`, `model_complexity=1`, `min_confidence=0.5`, `smooth_landmarks=True`였다(`detector/holistic.py`, `requirements.txt`). JS 라이브러리는 같은 모델이라는 보장이 없어 같은 영상으로 파이썬과 JS 출력을 비교했고, 그 결과로 레거시 holistic의 고정을 권장한다(7.1). 다만 파이썬과 좌표가 같지는 않고, 비교는 AI Hub 영상 클립으로 한 것이다.
- **손 z 값의 척도.** 손의 z를 `z / 척도`로 쓰는 것은 학습 쪽 정의를 그대로 따른 것이다. 종횡비 보정은 y에만 적용했고 z는 보정하지 않았다(MediaPipe의 z가 x와 비슷한 척도라는 가정).
- **단어 구간 자르기.** 학습 클립은 라벨의 단어 구간 경계로 잘린 것이다. 기능명세서는 손을 내린 시점을 기준으로 프런트가 구간을 자르도록 정했고, 이 구간 분리기가 실제로 어떻게 동작하는지는 확인하지 못했다. 경계 오차에 대한 평가는 따로 돌린 실험(`run_boundary16.ps1`)이 있고, 현재 (30, 49, 2) 모델에 대한 평가는 0항에 정리했다.
- **실제 웹캠 성능.** 현재 정확도는 모두 같은 촬영 환경의 AI Hub 영상에서 화자 단위로 나눠 잰 값이다. 웹캠으로 화면 속 영상을 다시 찍어 파이프라인이 동작함은 확인했지만(7.3), 사람이 직접 한 수어로는 측정하지 않았다.
- **지연 시간.** 엔드포인트를 직접 호출한 시험(2026-11-06, 요청 약 30KB, 시험 3건)에서 서버리스 첫 호출(콜드 스타트)은 9,154ms, 이후 호출은 67~105ms였다. 3초 요구를 맞추려면 시연 전에 미리 호출해 엔드포인트를 깨워 두는 등의 대응이 필요하다. 프론트, API Gateway, Lambda를 포함한 응답 시간은 재지 못했다.

| | 레거시 `@mediapipe/holistic` 0.5.1675471629 | `@mediapipe/tasks-vision` 1.2.0 (HolisticLandmarker) |

### 7.3 웹캠 파이프라인 확인

웹캠 테스트 페이지(레거시 JS, 반전 없는 프레임)로 AI Hub 클립을 두 번째 화면에 재생해 녹화하고, 이 규격의 요청 형식으로 엔드포인트 입력 경로(`predict_fn`)를 돌렸다. 이전 최종 모델(`noface` + 팔 z 이동 증강)로 어휘 안 클립 5개를 확인했다.

- 화상 2개는 둘 다 1순위가 화상이었다(GRU 0.76, 0.68. CNN 0.41, 0.21).
- 체온 3개는 GRU가 모두 체온(288)을 1순위로 냈다(0.67 ~ 0.75). CNN은 2개에서 체온(2573)이 1순위였다. 두 클래스는 같은 이름의 다른 단어 id다.
- 어휘에 없는 검사 클립 3개의 1순위 확률은 0.28 이하였다. 표본이 적어 임계값으로 쓸 수 있는 기준은 아니다.
- 화면을 다시 찍은 영상이라 손이 검출된 프레임은 35 ~ 52%에 그쳤다.
- 이 클립들은 학습 데이터라서 일반화 성능이 아니라 파이프라인이 동작하는지에 대한 확인이다.

### 7.4 이전 최종 모델 구성 (`noface`, 원시 프레임 요청)

- 피처 집합은 `noface`(166개)다. 코·입 위치를 입력에서 뺀다. 웹캠에서는 머리의 높이가 학습 영상과 달라(학습의 코 y 평균 −0.60 ± 0.05, 웹캠 녹화 −0.41 ~ −0.48) 머리 위치 피처가 있는 모델은 이동이 있을 때 확률이 크게 떨어졌다.
- 학습 중 팔 z(포즈 13 ~ 16)를 샘플마다 무작위로 ±2.5(정규화 단위) 옮기는 증강을 80% 확률로 적용했다.
- 합성 이동 조건에서 5-fold 정확도는 깨끗한 조건과 거의 같았다(CNN 97.8%, GRU 97.3%). 이동은 합성이고 시드는 1개다.

### 7.5 Tasks Vision 좌우 방향 확인 (Pose·Hand Landmarker)

| 입력 | 손 | 라벨이 가까운 손목과 일치 | 왼어깨(11)가 화면 오른쪽인 프레임 |

| 반전 없음 | 520 | 518 (99.6%) | 273/273 |

### 7.8 AI Hub 클립으로 본 학습 때 방식과 프론트 구성 (2026-11-08)

AI Hub 수어 클립 23개(모델 어휘에 있는 단어 12개, 없는 단어 11개)를 같은 프레임에서 두 방식으로 처리했다. 하나는 학습 때와 같은 파이썬 MediaPipe Holistic이고, 다른 하나는 7.7과 같은 구성의 Tasks Vision(`PoseLandmarker`(`pose_landmarker_full`) + `HandLandmarker`, VIDEO 모드, 옵션 기본값, 손 칸은 `handedness` 라벨 그대로)이다. 영상을 1920×1080 원본으로 풀어 반전 없이 넣었고, 프레임 시각은 30fps로 매겼다. 클립마다 검출기를 새로 만들어 추적 상태를 초기화했다. 두 방식의 좌표를 같은 변환(`spec2d.py`)에 넣어 현재 모델(`spec2d_noface` CNN, 178클래스)로 채점했다. 새 수어자에 대한 값은 REAL02, REAL06을 빼고 학습한 평가용 모델(`holdout_cnn`, 0항의 팀 val 실험에 쓴 모델, 최종 모델과 구조·하이퍼파라미터·클래스가 같다)로도 채점해 따로 적었다. 어휘 안과 밖은 학습 색인(`index.csv`)의 단어 번호로 나눴다. 어휘 안 12개의 구간은 영상 전체를 파이썬 Holistic으로 돌려 학습 키포인트 CSV와 가장 비슷한 연속 프레임(길이는 CSV의 프레임 수)을 찾아 정했다. 학습에 쓴 프레임과 완전히 같다는 보장은 없다.
